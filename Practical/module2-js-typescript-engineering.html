Section 01

ES6+ Essentials for Framework Engineering

Modern frameworks are written in and consumed through ES6+ JavaScript. Understanding these features is not optional — they show up constantly in React, Vue, and Angular source code, documentation, and community patterns. Below are the eight features you must internalise.

Destructuring
Extract values from objects/arrays into named variables. Ubiquitous in component props, hooks, and API responses.
const { name, age = 18 } = user;
const [first, ...rest] = arr;
Spread / Rest
Spread expands iterables; Rest collects them. Essential for immutable state updates and variadic functions.
const next = { ...state, count: 5 };
merge(...arrays);
Arrow Functions
Concise syntax that lexically binds this. Eliminates the class callback bind ceremony.
const double = x => x * 2;
items.map(i => i.id);
Template Literals
Multi-line strings with embedded expressions. Used for dynamic class names, styled-components, and GraphQL queries.
`Hello, ${name}!`
`btn ${active ? 'on' : 'off'}`
Optional Chaining ?.
Safe property access on nullable values. Replaces dozens of && guard chains in data-driven UIs.
user?.profile?.avatar
data?.[0]?.name
Nullish Coalescing ??
Returns right-hand side only when left is null/undefined. Safer than || which also catches 0 and "".
value ?? 'default'
count ?? 0 // 0 is valid!
Short-circuit Evaluation
Conditional rendering in JSX. && renders right side only when left is truthy; || is the fallback pattern.
isLoggedIn && <Dashboard />
title || 'Untitled'
Object Shorthand
When property name equals variable name, omit the repetition. Standard in reducers, API payloads, and component props.
// { name: name } →
{ name, age, onClick }

A Framework-Realistic Example

Real framework code uses all of these together. Here's a function that could live inside any React or Vue project:

javascript — all features working together 
// fetchUserData: uses destructuring, optional chaining,
// nullish coalescing, template literals, spread, and arrow functions

const fetchUserData = async ({ userId, fields = ['name', 'email'] }) => {
  const url = `/api/users/${userId}?fields=${fields.join(',')}`;

  const response = await fetch(url);
  const data     = await response.json();

  // Optional chaining: safe traversal of deeply nested response
  const avatar  = data?.profile?.media?.[0]?.url;

  // Nullish coalescing: 0 is a valid displayName, don't falsy-check it
  const displayName = data?.name ?? 'Anonymous';

  // Spread for immutable merge — never mutate `data` directly
  return { ...data, avatar, displayName };
};

// Usage with destructuring at the call site:
const { name, email, avatar } = await fetchUserData({ userId: 'u42' });
⚠ The || vs ?? Trap

Using || for defaults is a classic bug: count || 0 replaces count with 0 when count is already 0 (a valid value). Use ?? when you only want to handle null/undefined. This trips up nearly every developer coming from pre-ES2020 codebases.

📌 Key Points — Section 01

  • Destructuring eliminates repetitive property access — it's in virtually every hook, selector, and component.
  • Spread (...) is the primary tool for immutable state updates — creates new object/array references.
  • Optional chaining (?.) makes API response handling safe without verbose null guards.
  • ?? (nullish coalescing) is safer than || for defaults — it respects falsy values like 0 and "".
  • Arrow functions lexically bind this — eliminating the bind ceremony in class-based patterns.
Section 02

Closures as Memory / State Constructs

A closure is what happens when a function remembers the variables from the scope where it was defined, even after that scope has finished executing. This isn't a niche concept — it is literally how useState, event handlers, memoisation, and module privacy all work.

🔦 Analogy — The Backpack

When a function is created inside another scope, it packs up all the variables it references into an invisible backpack. Wherever that function travels — even if it's called later, by a completely different piece of code — it opens the backpack and uses those original variables. This backpack is the closure.

javascript — closure as a counter (the simplest state machine) 
// makeCounter returns a function — that function closes over `count`
function makeCounter(initial = 0) {
  let count = initial; // ← this lives in the closure (the "backpack")

  return {
    increment: () => ++count,
    decrement: () => --count,
    value:     () => count,
    reset:     () => { count = initial; },
  };
}

const counter = makeCounter(10);
counter.increment(); // 11
counter.increment(); // 12
counter.decrement(); // 11
console.log(counter.value()); // 11 — `count` persists between calls!

// `count` is private — only accessible via the returned methods
// This is the module pattern and it's also how class instances work

Closures Inside React: The Stale Closure Problem

React's functional component model is built entirely on closures. Each render creates a new closure that captures the state and props at that moment. This leads to a critical gotcha called the stale closure:

❌ Stale Closure Bug
function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      // This callback closes over
      // `count` from the FIRST render!
      // It will always be 0. 🐛
      setCount(count + 1);
    }, 1000);
    return () => clearInterval(id);
  }, []); // empty deps → runs once
}
✅ Functional Updater Fix
function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      // Functional updater: React passes
      // the current value — no stale ref!
      setCount(c => c + 1); // ✓
    }, 1000);
    return () => clearInterval(id);
  }, []);
}

Closures Power Custom Hooks

jsx — useLocalStorage: closure capturing key and serialisation logic 
// The returned [value, setValue] pair closes over `key` for the hook's lifetime
function useLocalStorage(key, initialValue) {
  const [stored, setStored] = useState(() => {
    // Lazy initialiser: runs once, not on every render
    try {
      const item = window.localStorage.getItem(key); // `key` from closure
      return item ? JSON.parse(item) : initialValue;
    } catch { return initialValue; }
  });

  const setValue = (value) => {
    try {
      window.localStorage.setItem(key, JSON.stringify(value)); // `key` from closure
      setStored(value);
    } catch (e) { console.error(e); }
  };

  return [stored, setValue]; // Both functions carry `key` in their backpack
}

// Usage:
const [theme, setTheme] = useLocalStorage('theme', 'dark');
// setTheme always knows which localStorage key to use — closure!
💡 Engineering Insight

useState itself is implemented using closures inside React's reconciler. Each call to useState captures a "slot" in a linked list of state hooks. The getter and setter functions form a closure over that slot. This is why hooks must always be called in the same order — it's positional, not named.

📌 Key Points — Section 02

  • A closure is a function that remembers its surrounding scope — the "backpack" of variables it was created with.
  • Every React functional component render creates a new closure with a snapshot of state/props at that moment.
  • Stale closures occur when an event/timer captures old state — fix with functional updaters or dependency arrays.
  • Closures are the mechanism behind private state, custom hooks, memoisation, and the module pattern.
  • Understanding closures = understanding the actual behaviour of hooks, not just their API.
Section 03

Functional Programming in UI

Functional programming (FP) isn't a separate paradigm you apply in Haskell. Modern UI development is deeply functional: map for rendering lists, filter for search results, reduce for computing totals, function composition for middleware and selectors. Understanding FP at the UI level makes your code predictable, testable, and composable.

The Three Workhorses

javascript — map, filter, reduce in UI context 
const products = [
  { id: 1, name: 'Keyboard', price: 129, inStock: true  },
  { id: 2, name: 'Mouse',    price: 59,  inStock: false },
  { id: 3, name: 'Monitor',  price: 399, inStock: true  },
];

// ─── MAP: Transform every element → renders a list of components ───
const cards = products.map(p => (
  <ProductCard key={p.id} product={p} />
));
// map doesn't mutate — it returns a NEW array of transformed values

// ─── FILTER: Keep elements matching a predicate → search / filters ───
const available = products.filter(p => p.inStock);
// filter doesn't mutate — returns a NEW filtered array

// ─── REDUCE: Collapse array to a single value → totals, grouping ───
const cartTotal = products
  .filter(p => p.inStock)       // chain: only in-stock items
  .reduce((sum, p) => sum + p.price, 0); // accumulate
// cartTotal: 528 (129 + 399)

// Advanced reduce: group by a property (building lookup tables)
const byId = products.reduce((acc, p) => ({ ...acc, [p.id]: p }), {});
// byId: { 1: {...Keyboard}, 2: {...Mouse}, 3: {...Monitor} }
// Used in normalised state (Redux pattern) for O(1) lookup

Function Composition

Composition means building complex operations from simple ones by chaining them. In UI, this shows up in middleware pipelines, selector chains, and data transformation pipelines.

javascript — compose and pipe patterns 
// compose: right-to-left application  f(g(h(x)))
const compose = (...fns) => x => fns.reduceRight((v, f) => f(v), x);

// pipe:    left-to-right (more readable for data pipelines)
const pipe    = (...fns) => x => fns.reduce((v, f) => f(v), x);

// Small, focused, testable functions:
const normalise  = (s) => s.trim().toLowerCase();
const truncate   = (n) => (s) => s.length > n ? s.slice(0, n) + '…' : s;
const capitalise = (s) => s.charAt(0).toUpperCase() + s.slice(1);

// Compose them into a display formatter:
const formatLabel = pipe(normalise, truncate(24), capitalise);

formatLabel('  HELLO WORLD THIS IS A VERY LONG TITLE  ');
// → 'Hello world this is a ve…'

// Used extensively in Redux middleware (applyMiddleware is compose!),
// React Higher-Order Components, and functional selector patterns.
🔦 Analogy — Unix Pipes

Function composition is the same idea as Unix command piping: cat file.txt | grep "error" | sort | uniq. Each command does one thing well and passes its output to the next. In JS: pipe(parseCSV, filterEmpty, sortByDate, formatForUI)(rawData). Every step is independently testable and replaceable — the Unix philosophy applied to functions.

📌 Key Points — Section 03

  • map transforms every element → used for rendering lists of components from data arrays.
  • filter keeps matching elements → used for search results, conditional lists, toggled views.
  • reduce collapses an array to a value → totals, normalised state objects, group-by operations.
  • None of these mutate the original array — they are the foundation of immutable data transformation.
  • Function composition (pipe/compose) builds complex data transformations from simple, testable pieces.
Section 04

Immutability and Pure Functions

Immutability and pure functions are not just academic concepts — they are the engineering contract that makes change detection, time-travel debugging, and predictable re-renders possible.

Pure Functions: The Contract

A function is pure if: 1) given the same inputs, it always returns the same output, and 2) it produces no side effects (no mutations, no I/O, no randomness).

❌ Impure — unpredictable
let taxRate = 0.2; // external dep

// Reads external state → impure
function getTotal(price) {
  return price * (1 + taxRate);
}
// Same input, different output
// if taxRate changes → bug!

// Mutates its argument → impure
function addItem(cart, item) {
  cart.push(item); // ← mutation!
  return cart;
}
✅ Pure — predictable
// All dependencies are explicit params
function getTotal(price, taxRate) {
  return price * (1 + taxRate);
}
// getTotal(100, 0.2) is ALWAYS 120
// Easy to test, easy to reason about


// Returns new array — never mutates
function addItem(cart, item) {
  return [...cart, item]; // new ref ✓
}

Why Immutability Matters for Frameworks

How Immutability Enables Efficient Change Detection

Immutable Update Patterns Cheatsheet

javascript — immutable update patterns you need to know 
// ─── Adding to an array ───
const addItem = (arr, item) => [...arr, item];

// ─── Removing by index ───
const removeAt = (arr, i) => arr.filter((_, idx) => idx !== i);

// ─── Updating by id ───
const updateById = (arr, id, patch) =>
  arr.map(item => item.id === id ? { ...item, ...patch } : item);

// ─── Updating a nested field ───
const setNestedField = (state) => ({
  ...state,
  user: {
    ...state.user,
    address: {
      ...state.user.address,
      city: 'Hyderabad'
    }
  }
});
// Spread only the path from root to the changed field
// Unchanged siblings are reference-shared (no cloning cost)

// ─── Toggling a boolean ───
const toggle = (state, key) => ({ ...state, [key]: !state[key] });
💡 Immer: Immutability with Mutable Syntax

For deeply nested state, spread syntax becomes verbose. Immer (used inside Redux Toolkit) lets you write mutating-style code that produces immutable updates under the hood. produce(state, draft => { draft.user.address.city = 'Hyderabad'; }) — Immer tracks all mutations and creates a new immutable tree.

📌 Key Points — Section 04

  • Pure functions: same input → same output, no side effects. They are the foundation of testable, predictable UI logic.
  • Immutability enables reference equality checks — the cheapest possible change detection (old === new).
  • Mutating state directly creates the same object reference → framework detects no change → silent UI bug.
  • Master the spread patterns: add ([...arr, item]), remove (filter), update (map + spread), nested (spread the path).
  • Immer provides ergonomic immutability for complex nested state — it's used in Redux Toolkit by default.
Section 05

Module Patterns

ES Modules (ESM) are the standard way to split JavaScript code into files with explicit, static imports/exports. Every modern framework and build tool (Vite, webpack, esbuild) is built around ESM. Understanding module semantics is crucial for tree-shaking, code-splitting, and managing circular dependencies.

ESM Syntax

javascript — named vs default exports 
// ─── math.js — named exports (multiple per file) ───
export const add  = (a, b) => a + b;
export const sub  = (a, b) => a - b;
export const mul  = (a, b) => a * b;
// No default export — consumers must use { } syntax

// ─── UserCard.jsx — default export (one per file, for components) ───
export default function UserCard({ user }) { ... }
// Consumer can name it anything: import Card from './UserCard'

// ─── Consuming both ───
import UserCard          from './UserCard';       // default
import { add, mul }    from './math';            // named
import { add as plus }  from './math';            // aliased
import * as Math         from './math';            // namespace import

Tree Shaking — Why Named Exports Matter

🌳 Analogy — Tree Shaking

Imagine your entire codebase is a tree. Tree shaking is a build-time process that identifies and drops branches (code paths) that are never used. It works by statically analysing import/export statements. Named exports allow the bundler to include only the functions you actually import. Barrel exports (export * from ...) and import * can defeat tree-shaking — the bundler must assume everything might be used.

❌ Kills Tree-Shaking
// Importing the whole module
import * as Icons from 'react-icons';
// Bundles ALL icons (~1MB+) even
// if you use only 2

import _ from 'lodash';
// Full lodash (~70KB) in bundle
// for one function
✅ Tree-Shakeable
// Named imports → tree-shakeable
import { FaUser, FaCog } from
  'react-icons/fa';
// Only those two icons bundled

import { debounce } from
  'lodash-es';
// Only debounce (~2KB) bundled

Barrel Files (index.ts) — Convenience vs Cost

typescript — barrel file pattern 
// components/index.ts — re-exports for clean import paths
export { default as Button   } from './Button';
export { default as Modal    } from './Modal';
export { default as Spinner  } from './Spinner';

// Consumers import cleanly:
import { Button, Modal } from '@/components';
// Instead of:
// import Button  from '@/components/Button/Button'
// import Modal   from '@/components/Modal/Modal'

// ⚠ Barrel files can slow cold-start (dev server) if they re-export
// hundreds of modules — use sparingly in very large codebases

📌 Key Points — Section 05

  • ESM uses static import/export — the bundler can analyse dependencies at build time (enabling tree-shaking).
  • Named exports are tree-shakeable; import * forces the entire module into the bundle.
  • One default export per file suits components; named exports suit utilities and constants.
  • Barrel files (index.ts) clean up import paths but can hurt dev-server cold start in massive monorepos.
  • Always use lodash-es (ESM build) over lodash (CommonJS) for tree-shaking to work.
Section 06

Async/Await and Promise Chains for UI Updates

UI development is inherently asynchronous — network requests, timers, animations, file reads. Mastering async patterns means the difference between a UI that feels alive and one riddled with race conditions and uncaught errors.

The Async Mental Model

Promise State Machine
javascript — async/await with UI state management 
// A complete async data-fetching pattern used in real components:

function useUserData(userId) {
  const [state, setState] = useState({
    data:    null,
    loading: true,
    error:   null,
  });

  useEffect(() => {
    let cancelled = false; // ← race condition guard (explained below)

    const load = async () => {
      setState(s => ({ ...s, loading: true, error: null }));

      try {
        const res  = await fetch(`/api/users/${userId}`);
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const data = await res.json();

        if (!cancelled) // Only update if still mounted
          setState({ data, loading: false, error: null });

      } catch (err) {
        if (!cancelled)
          setState({ data: null, loading: false, error: err.message });
      }
    };

    load();
    return () => { cancelled = true; }; // Cleanup: cancel on unmount/re-run
  }, [userId]); // Re-fetch when userId changes

  return state;
}

Race Conditions in Async UI

☠ Race Condition — Async UI's Hidden Enemy

If userId changes while a fetch is in-flight, two fetches run concurrently. The earlier fetch may resolve after the later one, leaving the UI in a stale state. The cancelled flag in the example above is the classic fix — the cleanup function sets it to true, and any pending response that resolves after cleanup is discarded. This pattern is so common it was the main motivation for AbortController.

Promise Combinators for UI

javascript — when to use Promise.all, allSettled, race 
// Promise.all — fetch in parallel, fail fast on any error
// Use: loading a dashboard where ALL data is required
const [user, posts, notifications] = await Promise.all([
  fetchUser(id),
  fetchPosts(id),
  fetchNotifications(id),
]);

// Promise.allSettled — run all, collect results even if some fail
// Use: loading optional widgets — show what succeeded
const results = await Promise.allSettled([
  fetchWidget1(), fetchWidget2(), fetchWidget3()
]);
const successful = results
  .filter(r => r.status === 'fulfilled')
  .map(r => r.value);

// Promise.race — use the fastest result
// Use: timeout pattern
const withTimeout = (promise, ms) =>
  Promise.race([
    promise,
    new Promise((_, reject) =>
      setTimeout(() => reject(new Error('Timeout')), ms)
    )
  ]);

📌 Key Points — Section 06

  • Always model async UI with a three-state object: { data, loading, error } — never leave any state undefined.
  • Always guard against race conditions with a cancelled flag or AbortController.
  • Check response.ok — fetch only throws on network failure, not on HTTP 4xx/5xx.
  • Promise.all: parallel + fail-fast. Promise.allSettled: parallel + resilient. Promise.race: timeout patterns.
  • Never call an async function directly in useEffect — define the async function inside and call it.
Section 07

Error Boundaries at the JS Level

In production, errors are inevitable. A well-engineered frontend has layered error handling: synchronous try/catch for predictable failure points, custom error types for categorisation, and error propagation strategies that prevent cascading failures.

Custom Error Classes — Typed Failures

javascript — error hierarchy for a frontend app 
// A typed error hierarchy lets you handle failures differently by category

class AppError extends Error {
  constructor(message, public readonly code: string) {
    super(message);
    this.name = 'AppError';
  }
}

class NetworkError extends AppError {
  constructor(status: number, url: string) {
    super(`HTTP ${status} at ${url}`, 'NETWORK_ERROR');
    this.name = 'NetworkError';
  }
}

class ValidationError extends AppError {
  constructor(field: string, message: string) {
    super(`${field}: ${message}`, 'VALIDATION_ERROR');
    this.name = 'ValidationError';
  }
}

// Typed handling: different UX for different error categories
function handleError(err: unknown) {
  if (err instanceof NetworkError)
    showToast('Connection problem. Please check your network.');
  else if (err instanceof ValidationError)
    setFieldError(err.message);
  else
    reportToSentry(err); // Unexpected — log to monitoring
}

The Error Boundary Pattern

Layer 1 — Global Async
window.addEventListener('unhandledrejection', handler) — catches unhandled promise rejections at the app level. The last safety net.
Layer 2 — Component Error Boundary
React ErrorBoundary class component catches render/lifecycle errors in the React tree. Prevents the whole app from crashing when one widget fails.
Layer 3 — Service/Hook Level
try/catch in async functions, custom useAsync hooks, and query libraries (React Query, SWR) catch errors before they surface to the component.
Layer 4 — Input Validation
Zod / Yup schemas validate API responses and user inputs before they enter state. Fail loudly at the boundary, not silently deep in the render tree.
jsx — React Error Boundary + safe async data display 
// Error Boundary: class component (only way to catch render errors)
class ErrorBoundary extends React.Component {
  state = { hasError: false, error: null };

  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  componentDidCatch(error, info) {
    reportToSentry(error, info.componentStack); // Always log!
  }

  render() {
    if (this.state.hasError)
      return this.props.fallback ?? <div>Something went wrong.</div>;
    return this.props.children;
  }
}

// Wrap risky sections — not the entire app
function App() {
  return (
    <div>
      <Header />  ← never wrapped (critical shell)
      <ErrorBoundary fallback={<WidgetError />}>
        <Dashboard />  ← wrapped: dashboard can fail without breaking header
      </ErrorBoundary>
    </div>
  );
}

📌 Key Points — Section 07

  • Custom error classes let you handle failures differently by category — network, validation, unexpected.
  • Always type-check caught errors: if (err instanceof NetworkError) before accessing custom properties.
  • Layer your error handling: global handler → Error Boundary → hook/service → input validation.
  • Error Boundaries only catch render/lifecycle errors — they don't catch async errors (that's try/catch's job).
  • Wrap sections of the UI in Error Boundaries, not the entire app — contain failures, don't hide them.
Section 08

TypeScript Types, Interfaces & Generics

TypeScript adds a static type layer over JavaScript that catches entire classes of bugs at compile time — the wrong prop type, a missing null check, an impossible state. For UI engineering, it's not optional — it's the contract between components.

Types vs Interfaces

interface
For object shapes and class contracts. Supports declaration merging (extend later). Preferred for component props and API response shapes.
type
For everything else: union types, tuples, mapped types, conditional types. More expressive than interface for complex type algebra.
Generics
Type variables that let you write reusable, type-safe code across different data shapes — like function parameters but for types.
Utility Types
Built-in type transformers: Partial, Required, Pick, Omit, Readonly — manipulate existing types without repetition.
typescript — interfaces and types for UI components 
// ─── Interface: object shapes (component props) ───
interface User {
  id:       string;
  name:     string;
  email:    string;
  role:     'admin' | 'editor' | 'viewer'; ← literal union
  avatar?:  string;   ← optional field
}

interface UserCardProps {
  user:         User;
  onEdit?:      (id: string) => void;  ← optional callback
  isSelected?:  boolean;
}

// ─── type: unions, tuples, mapped types ───
type LoadState<T> =
  | { status: 'idle'    }
  | { status: 'loading' }
  | { status: 'success'; data: T         } ← discriminated union
  | { status: 'error';   message: string  };
// TypeScript narrows the type in each case:
// if (state.status === 'success') state.data  ← data is now available
// if (state.status === 'error')   state.message ← message is now available

// ─── Utility types in practice ───
type CreateUserInput = Omit<User, 'id'>;  // User without id (server generates it)
type UserUpdate      = Partial<User>;       // All fields optional (PATCH request)
type DisplayUser    = Pick<User, 'id' | 'name' | 'avatar'>; // Only display fields
type FrozenUser     = Readonly<User>;      // All fields read-only (prevent mutation)

Generics — Writing Reusable, Type-Safe UI Logic

typescript — generics in components, hooks, and utilities 
// ─── Generic API hook ───────────────────────────────────────────
// T is a type variable — the consumer decides what T is
function useFetch<T>(url: string): LoadState<T> {
  const [state, setState] = useState<LoadState<T>>({ status: 'loading' });
  // ... fetch logic ...
  return state;
}

// Usage — T is inferred as User[]
const state = useFetch<User[]>('/api/users');
if (state.status === 'success') {
  state.data.map(u => u.name); // ← TypeScript knows data is User[]
}

// ─── Generic list component ─────────────────────────────────────
interface ListProps<T> {
  items:       T[];
  renderItem:  (item: T, index: number) => React.ReactNode;
  keyExtractor:(item: T) => string;
}

function List<T>({ items, renderItem, keyExtractor }: ListProps<T>) {
  return <ul>{items.map((item, i) =>
    <li key={keyExtractor(item)}>{renderItem(item, i)}</li>
  )}</ul>;
}

// Works for users AND products AND orders — one component, full type safety:
<List<User>
  items={users}
  keyExtractor={u => u.id}         ← TypeScript knows u is User
  renderItem={u => <UserCard user={u} />}
/>
🔦 Analogy — Cookie Cutters

Generics are like cookie cutters. The cutter's shape (the generic function) defines the structure of the operation, but the dough you press it into (the type argument T) determines the final cookie. useFetch<User[]> is the same cutter pressed into User[] dough — it produces a perfectly shaped LoadState<User[]> without you writing any new code.

📌 Key Points — Section 08

  • Use interface for object shapes and props; use type for union types, complex type algebra, and aliases.
  • Discriminated unions (status: 'success' | 'error') model all possible states explicitly — no impossible states.
  • Utility types — Partial, Omit, Pick, Readonly — derive new types from existing ones without repetition.
  • Generics write code once that works correctly across many types — essential for hooks, list components, and API utilities.
  • TypeScript's value is proportional to how strictly you use it — avoid any; use unknown for truly unknown types.

Architecture of a Front-End Codebase

A well-structured frontend codebase is the difference between a project that scales smoothly and one that becomes a maze after 6 months. The goal of architecture is to make the right thing easy and the wrong thing hard — through folder structure, module boundaries, and separation of concerns.

The Feature-Based Structure

There are two main schools: type-based (group by what it is: components/, hooks/, utils/) and feature-based (group by what it does: features/auth/, features/products/). Feature-based scales far better because related code stays co-located.

The Service Layer Pattern

Services abstract over infrastructure — they're the only place where raw API calls, localStorage, or analytics tracking happen. Components and hooks import from services — they never call fetch directly.

typescript — service layer: separating API concerns from UI logic 
// services/api/client.ts — One configured API client, used everywhere
import axios from 'axios';

export const apiClient = axios.create({
  baseURL: process.env.VITE_API_URL,
  timeout: 10_000,
});

// Interceptor: attach auth token to every request
apiClient.interceptors.request.use(config => {
  const token = getAuthToken();
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

// features/products/services/productApi.ts — domain service
import { apiClient } from '@/services/api/client';
import type { Product, CreateProductInput } from '../types';

export const productApi = {
  getAll: ()                  => apiClient.get<Product[]>('/products'),
  getById: (id: string)       => apiClient.get<Product>(`/products/${id}`),
  create: (data: CreateProductInput) => apiClient.post<Product>('/products', data),
  update: (id: string, data: Partial<Product>) =>
    apiClient.patch<Product>(`/products/${id}`, data),
  delete: (id: string)       => apiClient.delete(`/products/${id}`),
};

// features/products/hooks/useProducts.ts — hook uses service, not fetch
export function useProducts() {
  return useQuery({ queryKey: ['products'], queryFn: productApi.getAll });
}
// Components import useProducts — they have NO knowledge of API details

Layer Dependency Rules

Allowed Import Directions (Dependency Rule)
💡 The Rule: Dependencies Point Inward

Pages import from features. Features import from hooks and shared. Hooks import from services. Services import from nothing in the UI layer. This is The Dependency Rule — if a lower layer ever imports from a higher layer, you have a circular dependency. Tools like eslint-plugin-import and dependency-cruiser can enforce this automatically.

📌 Key Points — Section 09

  • Feature-based folder structure scales better than type-based — co-locate everything a feature needs.
  • Each feature exposes a public API via index.ts barrel — internal implementation details are private.
  • The service layer is the only place that calls APIs, touches localStorage, or fires analytics — components never call fetch directly.
  • Dependencies flow in one direction: pages → features → hooks → services. No circular imports.
  • Pages are thin orchestrators — they compose features but contain little logic themselves.
Knowledge Check
CO2 Module Quiz — 8 Questions
Question 1 of 8
What is the key difference between || and ?? for providing default values?
✓ Correct! count || 0 returns 0 even when count is already 0 (a valid value). count ?? 0 returns 0 only when count is null or undefined. This is a classic bug in forms and counters.
✗ || considers 0, "", false, null, and undefined as falsy. ?? (nullish coalescing) only triggers on null/undefined — so 0 ?? 'default' returns 0, while 0 || 'default' returns 'default'. Critical difference in counters and form fields.
Question 2 of 8
What is a "stale closure" in the context of React hooks?
✓ Correct! Each render creates a new closure over state/props at that moment. If an async callback or setInterval was created in an earlier render, it still references that render's values — leading to the "stale closure" bug. Functional updaters (setState(c => c + 1)) and correct dependency arrays fix this.
✗ A stale closure occurs when a callback (like a timer or event handler) was created in an earlier render and still holds a reference to the old state/props values — not the current ones. The fix is using functional updaters like setCount(c => c + 1).
Question 3 of 8
Which of these updates state immutably?
✓ Correct! Spread ([...prev.items, newItem]) creates a new array with a new reference. React detects the reference change and schedules a re-render. The other options all mutate the existing array in place — same reference, React sees no change.
✗ Only B is correct. [...prev.items, newItem] creates a new array (new reference). React compares references, not values. Mutating the existing array (push, assignment, Object.assign) keeps the same reference — React skips the re-render entirely.
Question 4 of 8
Why does importing with import * as _ from 'lodash' hurt bundle performance?
✓ Correct! Tree-shaking works by statically analysing named imports/exports. import * imports the entire namespace — the bundler can't know at build time which properties will actually be accessed, so it includes everything. Use import { debounce } from 'lodash-es' instead.
✗ The issue is tree-shaking. Bundlers (Vite, webpack) eliminate unused exports statically. Namespace imports (import *) defeat this because the bundler can't know which properties will be accessed at runtime — it must include the entire library.
Question 5 of 8
In Promise.all([fetchA(), fetchB(), fetchC()]) — what happens if fetchB rejects?
✓ Correct! Promise.all is "fail-fast" — one rejection causes the whole promise to reject immediately, even if other requests succeed. Use Promise.allSettled when you want all results regardless of individual failures (for optional dashboard widgets, for example).
✗ Promise.all fails fast — a single rejection causes the entire promise to reject immediately. Other in-flight requests are not cancelled (they run to completion) but their results are discarded. Use Promise.allSettled to handle partial failures gracefully.
Question 6 of 8
What does a React Error Boundary NOT catch?
✓ Correct! Error Boundaries only catch synchronous errors in the React rendering process (render, constructors, lifecycle methods). Async errors — inside setTimeout, fetch callbacks, or async event handlers — must be caught with try/catch and stored in component state to surface them to the Error Boundary.
✗ Error Boundaries don't catch async errors. They only intercept errors in the synchronous React rendering pipeline (render, constructors, getDerivedStateFromProps, componentDidMount/Update). For async errors, catch them in try/catch and call setState to surface them to the boundary.
Question 7 of 8
What TypeScript utility type would you use to create a type for a PATCH endpoint body, where all User fields are optional?
✓ Correct! Partial<T> makes all properties of T optional. Perfect for PATCH endpoints where the client sends only the fields it wants to update. Required<T> is the opposite (all required). Readonly<T> prevents mutation. Pick<T, K> selects a subset of fields.
✗ Partial<User> is the answer. It transforms all of User's fields to be optional (?:). Required does the opposite. Readonly prevents property mutation. Pick selects a named subset of fields. Together these are the most useful built-in utility types.
Question 8 of 8
In a feature-based architecture, which layer should directly call fetch() or axios.get()?
✓ Correct! The service layer is the boundary between UI code and infrastructure. It owns all HTTP calls, response parsing, and error normalisation. Hooks and components import from services — they never call fetch directly. This means you can swap axios for a different client in one place without touching any component.
✗ The service/API layer is the only place that should call fetch or axios. This separation means components have zero knowledge of how data is fetched — they only consume types and values. Swapping APIs, mocking for tests, and adding auth headers all happen in one place.

Summary

CO2 Module — Key Takeaways

The concepts in this module are the language-level substrate that frameworks sit on. Master these and framework code stops being magic.

⚡

ES6+ Syntax

Destructuring, spread, optional chaining (?.), and nullish coalescing (??) are the daily vocabulary of framework code — not syntactic sugar, but functional tools.

🎒

Closures = State

Every hook, every custom callback, every module encapsulates state through closures. Stale closures cause silent bugs — use functional updaters and correct dependency arrays.

🔗

FP Primitives

map, filter, reduce, and pipe replace imperative loops and mutation. They are the foundation of list rendering, data transformation, and middleware pipelines.

🧊

Immutability

New reference = change detected. Never mutate state in place. Spread creates the new reference. Immer provides ergonomic syntax for deep trees.

🌳

ESM + Tree-Shaking

Named imports allow bundlers to eliminate dead code. Avoid import * from large libraries. Barrel files help DX but should be used with awareness of cold-start costs.

⏳

Async Mastery

Always model three states: loading / data / error. Guard against race conditions. Choose Promise.all vs allSettled intentionally. fetch doesn't throw on 4xx — always check response.ok.

🛡️

Layered Error Handling

Typed errors, Error Boundaries, and global handlers create a safety net. Errors surface at the right layer — not silently, not catastrophically.

🔷

TypeScript Contracts

Discriminated unions eliminate impossible states. Generics write logic once across many types. Utility types (Partial, Omit, Pick) derive without repetition.

🏗️

Architecture

Feature-based structure. Services own HTTP calls. Dependencies flow inward. Barrel files expose a controlled public API per feature. Pages are thin orchestrators.

💡 The Through-Line

Every concept in this module is about one thing: making behaviour predictable and testable. Pure functions are predictable. Immutability makes change traceable. Typed errors make failures explicit. A layered architecture makes each piece independently testable. This is what separates engineering from scripting.
